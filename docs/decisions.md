# 設計判断の記録

設計議論の経緯を、判断ごとに「決定 / 理由 / 検討した代替案 / 見直す条件」で残す。
新しい判断は末尾に D-xx の連番で追記する。既存の判断を覆す場合は、元のエントリを消さずに「→ D-yy で変更」と追記する。

---

## D-01 インオーダー・スカラーから始める
- **決定**: 最初のコアはインオーダー・スカラー
- **理由**: 趣味で Linux 起動まで到達することを優先。特権アーキテクチャとメモリ系の検証に集中できる
- **代替案**: 最初からスーパースカラ / アウトオブオーダー
- **見直す条件**: M5 達成後（D-28）

## D-02 ISA は RV64IMA_Zicsr_Zifencei_Zicntr + S/U + Sv39
- **決定**: 上記を中心 ISA とし、C/F/D/Sstc/Zicbom などは後で追加
- **理由**: OpenSBI の要件は rv64ima_zicsr + S-mode + mtvec のダイレクトモードで足りる（PMP、TIME CSR は任意）。Linux も `CONFIG_RISCV_ISA_C=n`、`CONFIG_FPU=n` でビルドでき、ユーザーランドは Buildroot の lp64 で用意できる
- **代替案**: 最初から RV64GC（既製ディストリビューションが使える）
- **見直す条件**: 既製ディストリビューションを使いたくなったとき（RV64GC が必要）

## D-03 マイルストーンの順序: キャッシュより先に Linux
- **決定**: M0 基盤 → M1 特権+Sv39 → M2 OpenSBI → M3 Linux（キャッシュなし）→ M4 キャッシュ/バス → M5 FPGA
- **理由**: 特権アーキテクチャとキャッシュを同時に立ち上げると原因の切り分けが難しい。M3 の Linux 起動を M4 の強力な退行テストに使える。OpenSBI の起動は手前の良い区切り。`rv64ui-v-*` で Sv39 を OpenSBI より前に試験できる
- **前提条件**: M0 からメモリインタフェースを ready/valid・可変待ち時間対応にしておく
- **代替案**: キャッシュを先に作る（当初案）
- **見直す条件**: なし

## D-04 7 段パイプライン（F0 F1 F2 [FB] D X M W）
- **決定**: フロントエンド 3 段 + Fetch Buffer + バックエンド 4 段
- **理由**: FPGA の BRAM は同期読み出しなので I$ 読み出しに 1 段丸ごと必要。F2 で整列/早期リダイレクト。Fetch Buffer でフロントエンドとバックエンドのストールを切り離す（ストール信号の全段伝搬がタイミングのボトルネックになるため）
- **代替案**: 古典的 5 段（I$ を LUTRAM や ASIC 前提にするなら可能）
- **見直す条件**: タイミング評価で段の過不足が判明したとき

## D-05 I$ は 16KB 4-way 64B VIPT、FDIP は不採用
- **決定**: 1way=4KB で VIPT のエイリアスを回避。valid は FF で一括無効化。8B/cycle フェッチ。ブロッキング + next-line プリフェッチ
- **理由**: iTLB と I$ を同サイクルで引ける。後で問い合わせ（スヌープ）を受ける際も物理アドレス下位 12bit でそのまま引ける。FDIP は分岐予測器が十分先行できる幅広いコアで効くもので、スカラーでは割に合わない
- **参考**: XiangShan 昆明湖は 64KB 4-way + FDIP + WayLookup、P870 は 64KB/36B フェッチ、C910 は 64KB 2-way + プリデコードビット、Veyron V1 は 512KB の命令専用階層
- **見直す条件**: 性能測定で I$ ミスが支配的なとき（容量増は way 増で）

## D-06 C 拡張は Linux 起動後。ただし最初から準備する
- **決定**: C 拡張は M3 以降。PC の bit1 を残す、`is_rvc` を全段に流す、Fetch Buffer をハーフワード単位、展開器の差し込み口を用意
- **理由**: 特権アーキテクチャの検証時に命令境界のバグを混ぜないため。C 拡張の大変な部分は展開器ではなく、フェッチ整列・ラインまたぎ・例外条件（IALIGN、stval）・BTB・リンクアドレス・misa への波及で、準備しておけば改修は小さい
- **代替案**: 最初から C 拡張
- **見直す条件**: なし（C 拡張でコードサイズが 2〜3 割縮み I$ に効くので、性能測定の頃には入れる）

## D-07 Fetch Buffer はハーフワード単位の FIFO で、整列は出口
- **決定**: F2 は 4 ハーフワードをマスク付きで push、出口で `is_rvc` を見て 1/2 個 pop。例外情報はハーフワードごと
- **理由**: ライン/ページをまたぐ命令の特別処理が不要。出口論理が小さくタイミングに優しい。2-way への拡張が容易
- **代替案**: F2 に独立した整列バッファ（余り 16bit の持ち越し）
- **見直す条件**: なし

## D-08 分岐予測は段階的。BTB はペナルティ 1 サイクル構成から
- **決定**: not-taken → F2 で JAL/BTFN → BTB（BRAM）+ bimodal + RAS。BTB はフェッチブロック単位
- **理由**: F0 で同サイクルに次 PC を決めるゼロバブル構成は FPGA でクリティカルパスになりやすい。フェッチブロック単位にするのは RVC で 1 ブロックに複数分岐が入りうるため（XiangShan の FTB の考え方）
- **見直す条件**: 性能測定で taken 分岐のバブルが支配的なら L0 BTB、分岐ミスが支配的なら gshare

## D-09 プリデコード結果は当面 I$ に保存しない
- **決定**: スカラーでは F2 で命令ビットから計算する
- **理由**: RISC-V の命令長判定は 2bit 比較、分岐種別も数ゲートで、文脈に依存しない（x86 と違う）。当初「L1 に保存」を推奨したが訂正
- **見直す条件**: 2-way 化、F1 で分岐情報が必要になったとき、F2 のタイミングが厳しいとき（そのときはハーフワードあたり 4bit）

## D-10 L0（プリデコード/展開済み命令キャッシュ）は後回し
- **決定**: 他の改良をやり尽くしてから検討
- **理由**: プリデコード保持のための L0 は D-09 の理由で価値が小さい。L0 の本当の価値はヒット時のフロントエンド短絡だが、Linux のような大きな命令フットプリントではヒット率が低く、一貫性（VIVT なら sfence.vma、ASID、特権モード）と 2 系統のフェッチ経路の検証コストが高い
- **作るなら**: 展開済み命令のループバッファ型、フェッチブロック単位 4〜8 エントリ、VIVT + 権限ビット、L1 からのバイパス必須
- **見直す条件**: 性能測定後

## D-11 周波数目標と基準デバイス
- **決定**: xc7a100t-1、コア単体 OOC、配置配線後で、必達 100 / 目標 150 / 挑戦 200 MHz。M0 から合成を回して推移を記録
- **理由**: 周波数は段の切り方など構造で決まり後から上げにくい。FPGA では周波数が性能を大きく左右する。最も厳しい Artix-7 -1 を基準にすると構造判断を誤りにくい
- **参考**: VexRiscv（RV32）の Linux 互換構成は Artix-7 で 180MHz（コア単体、最速グレードと思われる）。RV64 + MMU で -1 の 200MHz はかなり挑戦的
- **注意**: 周波数目標で M3 までの進捗を止めない。構造に関わるもの（ロード使用サイクル数など）だけ最初から合わせる

## D-12 RTL は SystemVerilog
- **決定**: SystemVerilog
- **理由**: 実装者の経験。Verilator、Vivado、SymbiYosys に対応
- **影響**: Chisel 前提のエコシステム（rocket-chip、XiangShan の DiffTest）は直接は使わない（D-25）

## D-13 フラッシュは valid クリア + 一本のリダイレクトバス
- **決定**: 専用信号で各段の valid をクリア。発生源は一本のバスにまとめ、最も古い段を優先、フラッシュはストールより優先。分岐ミスのリダイレクトは 1 段レジスタ
- **理由**: データ部をリセット/クリアしなくて済む。発生源ごとの配線を増やさない。X での比較結果から F0 の BRAM アドレスまでを 1 サイクルに収めるのは FPGA で厳しい
- **付随規則**: I$ リフィルは完了させて結果を捨てる、MMIO は非投機、ストアバッファは消さない、長い演算は中止か結果破棄、スコアボードの印を解除、Fetch Buffer はポインタで一括クリア

## D-14 CSR 書き込みは全フラッシュから始める
- **決定**: 全 CSR 書き込みを確定後フラッシュ + 再フェッチ。性能測定後に影響範囲の分類（A〜E、design.md §3.4）で段階的に最適化。最初は sstatus.SIE
- **理由**: 考慮漏れがなく、Linux 起動までの正しさ確保を優先。ただし Linux では irqsave/irqrestore（SIE）、uaccess（SUM）、トラップ出入りで CSR 書き込みが頻繁なので、最終的には最適化が必要
- **注意**: 最適化は「めったに起きない条件でしか表に出ないバグ」を生みやすい。一段階ずつ広げ、毎回 Spike 比較を回す

## D-15 コア内部インタフェースは ready/valid
- **決定**: REQ（op, paddr, size/mask, wdata, id, src, attr）/ RESP（rdata, id, beat, last, err）。全体制御は req/done の専用信号、アドレス付き一貫性メッセージはチャネル
- **理由**: AXI と同じ規則で混乱しない。`beat` で WRAP バーストに対応、`id` で将来のノンブロッキング化に対応。無効化をチャネルにするのは、リフィルとの競合で順序を表現する必要があるため
- **代替案**: TileLink/ACE をコア内部まで通す

## D-16 データ側はキャッシュ側と MMIO 側の二つのポート
- **決定**: キャッシュ側 ACE 128bit、MMIO 側 AXI4-Lite 64bit。AXI4-Lite の幅制約に合わせる必要なし
- **理由**: 転送の性質（ライン単位バースト vs 1 ビート・副作用あり）が違う。HoL ブロッキングを防ぐ。将来キャッシュ側を一貫性プロトコルにしたときデバイスアクセスを混ぜずに済む（rocket-chip も同様に分離）
- **代償**: 二つのポート間の順序をコアが保証（MMIO は強い順序、`fence w,o` でキャッシュ側の B 応答を待つ）
- **関連**: CLINT/PLIC は 64bit 側（mtime の分割読みを避ける）、ブート ROM はキャッシュ可能領域（非キャッシュのフェッチ経路を作らない）

## D-17 キャッシュ側のバス幅は 128bit
- **決定**: 128bit。幅はパラメータ化
- **理由**: リフィル 4 ビート。小型ボードの MIG（16bit DDR3、4:1）のユーザー幅と合いやすい。64bit × 8 バンクの BRAM 構成と相性が良い。100〜150MHz でタイミング上の問題は小さい

## D-18 キャッシュ側プロトコルは ACE（段階的に使う範囲を広げる）
- **決定**: 段階 1 は実質 AXI4、段階 2 で ReadShared/WriteUnique/無効化応答と I$ の ReadClean、DMA は ACE-Lite、段階 3 で MESI 用トランザクション。RACK/WACK 必須、バリア不使用
- **理由**: 実装者に ACE/AXI の経験がある。FPGA の IP 資産は AXI 前提
- **代替案**: TileLink TL-C（一貫性規則は単純だが Chisel エコシステム中心）、CHI（大規模向け）、独自プロトコル
- **見直す条件**: 段階 3 の設計時に、L1-L2 間を独自プロトコルにする選択肢も再検討

## D-19 DMA との一貫性: Zicbom → L2 での IO コヒーレンシ
- **決定**: 段階 1 は Zicbom（Linux は非コヒーレント DMA に対応）。段階 2 で DMA ポートを共有 L2 に接続し、DT に `dma-coherent`
- **理由**: DMA デバイス自体は ACE を話す必要がなく（AXI4 マスタのまま、L2 が一貫性を解決）、段階 2 の「L1 ライトスルー + インクルーシブ L2」構成では IO コヒーレンシがほぼ追加コストなしで得られる
- **注意**: L2 で部分書き込みのマージ、DMA のミスはアロケートしない。順序問題（記述子の書き込み → ドアベル）は形を変えて残る。Zicbom は RVA22 以降に含まれ、非コヒーレントデバイス用にも段階 2 以降も実装する

## D-20 FENCE.I と I$ の一貫性
- **決定**: FENCE.I の仕事を (a) I$ リフィルが D$ の最新データを見る、(b) I$ の古いラインを捨てる、に分ける。(a) は L1 ライトスルー（段階 1/2）または一貫性のある読み出し（段階 3）で解決、(b) は段階 1 は一括無効化、段階 2 以降は L2 が I$ も追跡して無効化を送る
- **理由**: 多くの OSS コアが FENCE.I で D$ 全 dirty ラインを書き戻すのは (a) のためで、これがコストの大半。I$ は状態が無効/共有の二つだけで、問い合わせへの応答も無効化のみなので複雑さは小さい（Neoverse N1 や x86 も I$ はハードウェアで一貫性を保つ）。VIPT（D-05）なので物理アドレスでそのまま引ける
- **注意**: I$ が一貫性を保っても FENCE.I 命令自体（ストアバッファ排出、Fetch Buffer/L0 のフラッシュ）と、Linux のリモート FENCE.I（IPI）は残る。RISC-V には Arm の CTR_EL0.DIC に相当する標準の通知手段がない（と理解している）

## D-21 ロードの結果は 2 サイクル後に使用可能
- **決定**: ロード直後の依存命令は 2 サイクル待つ
- **理由**: 200MHz では BRAM 読み出し → way 選択 → 切り出し/符号拡張 → フォワードが 1 サイクルに収まらない。構造に関わるので最初から決める
- **見直す条件**: 目標周波数を下げる場合

## D-22 ストアバッファ
- **決定**: design.md §5.5 の構成。段階: 1〜2 エントリ・結合なし・一致したら待つ → 4〜8 エントリ・FENCE 待ち → 結合と転送
- **理由**: BRAM で D$ ストアが 2 サイクル（タグ読み → データ書き）かかりロードとポートを奪い合うため。ライトスルーの遅い経路をパイプラインから切り離すため
- **要点**: 下流の応答まで残す、アドレス比較だけ並列（ページ内オフセットで先行比較）、RVWMO なので結合可（FENCE/.rl をまたがない）、Ztso にはしない

## D-23 メモリマップは QEMU `virt` に準拠、定義は一か所
- **決定**: ブート ROM 0x1000、CLINT 0x0200_0000、PLIC 0x0c00_0000、UART 0x1000_0000、DRAM 0x8000_0000。一つの定義ファイルから RTL/DT/テストベンチ/Spike 設定を生成
- **理由**: RTL より先に同じ OpenSBI/Linux イメージを QEMU と Spike で検証できる。Spike の既定配置とも近い。五か所（RTL、DT、OpenSBI、リンカスクリプト、Spike）のずれを防ぐ
- **関連**: ブート ROM は Spike と同じ動作にし、同じ DTB を `--dtb` で渡す。CLINT の時間は DUT から注入

## D-24 実機ボードは riscv-tests 通過後に決める
- **決定**: 周波数追跡の合成対象（xc7a100t-1）だけ先に決め、実機ボードは後で。候補は xc7k325t-2、KR260、Arty A7-35T、Nexys A7
- **理由**: コアをボード非依存に作れば後で選んでも手戻りはほぼない
- **メモ**: KR260 は PS の HPC ポート（ACE-Lite、128bit）が今の設計と自然につながる。xc7k325t はライセンス要確認。Arty A7-35T は容量が窮屈な可能性

## D-25 協調シミュレーションは Spike を自前で接続（方針 B）
- **決定**: Verilator + Spike ライブラリの自前協調シミュレーションを M0 から作る。確定命令の記録は RVFI と DiffTest の `DiffInstrCommit` の中間の形式
- **理由**: SystemVerilog 設計では DiffTest（Chisel 推奨）をそのまま使うより、仕組みを把握できる自前実装が向く。記録形式を DiffTest に寄せておけば後で乗り換えも可能
- **DiffTest から借りる**: ストアバッファ排出時・リフィル時の検査、スナップショットからの自動再実行（LightSSS）
- **リファレンスモデル**: 最初は Spike（実績と情報量、キャッシュシミュレーション機能）。マルチコア段階でメモリモデル検査機能を持つ Whisper（Tenstorrent が開発継続）を検討
- **代替案**: DiffTest をそのまま使う（方針 A）、riscv-formal

## D-26 ファイル一覧の正は Verilator の `.f`
- **決定**: `core.f` / `soc.f` / `sim.f` の階層。合成可能部分の `.f` から後で Hog のリストファイルを生成
- **理由**: 序盤は Verilator 主体。Verilator の lint はツール非依存性を保つのにも役立つ
- **関連**: テクノロジーラッパー（`rtl/tech/generic` と `rtl/tech/xilinx`）で意図的な差分を一か所に集める
- **見直す条件**: 構成が増えて管理が煩雑になったら FuseSoC への一本化を検討

## D-27 FPGA プロジェクト管理は Hog（FPGA 実装段階で導入）
- **決定**: ボードごとのプロジェクト生成と git ハッシュの埋め込みに Hog を使う
- **理由**: サブモジュールとして入れるだけで使える。ビットストリームに git のタグ/ハッシュを埋め込める。`.xpr` を管理せずに済む
- **活用**: ハッシュを SoC 情報レジスタ / mimpid から読めるようにし、起動ログと確定命令の記録に RTL のコミットを対応付ける
- **代替案**: FuseSoC（シミュレーションと合成のファイル一覧を一元化）、LiteX（ボード支援が豊富だが DDR が LiteDRAM になり自前の ACE/L2 構成と別世界）

## D-28 将来の拡張はインオーダー 2-way を優先
- **決定**: スコアボード + ノンブロッキングキャッシュ → インオーダー 2-way。アウトオブオーダーは最後の選択肢
- **理由**: FPGA では多ポートのレジスタファイル、wakeup/select の CAM、広いバイパスが苦手で周波数が落ちやすい。コアのクロックが低く DRAM 待ちがサイクル換算で小さいため、アウトオブオーダーの主な利益（待ち時間の隠蔽）が薄い
- **2-way 方針**: 非対称パイプ、LSU 1 本、単純なペアリング、古い命令を pipe0
- **参考**: SiFive U74（VisionFive 2 で実測可能）、Cortex-A53/A55、NaxRiscv（FPGA 向け OoO）

## D-29 マルチコアは段階的に（ライトスルー L1 + インクルーシブ共有 L2 から）
- **決定**: 段階 2 の初版は L1 D$ ライトスルー、共有 L2 がどの L1 がラインを持つかを記録し、書き込み時に他の L1 を無効化。MESI は段階 3
- **理由**: L1 に MESI を実装するより大幅に単純で、複数コアでの Linux 起動までの距離が縮む。DMA の IO コヒーレンシ（D-19）と FENCE.I（D-20）も単純になる
- **代償**: L2 への書き込みトラフィックが増える

## D-30 ベンチマークと計測の方針
- **決定**: CoreMark/Embench は比較用の数字。フロントエンド評価は命令の使用範囲が大きいワークロード。Dhrystone は使わない。性能カウンタで CPI の内訳を作ることを重視。評価は「サイクルあたり性能 × 達成周波数」
- **理由**: CoreMark は I$ に収まり I$/分岐予測を評価できない。Dhrystone はコンパイラ最適化で数字が大きく変わる
